# Retrieval Evaluation — Recall@k / MRR / configuration ablation

Measures PaperTrail's retrieval quality directly — no LLM needed, since Recall@k
is a property of retrieval, not answer generation — and compares four
configurations of the stack.

```bash
python -m eval_recall.recall_eval                     # ablate all four configs
python -m eval_recall.recall_eval --config bm25       # one lane
python -m eval_recall.recall_eval --with-latency      # latency in the report file
python -m eval_recall.recall_eval --labeled q.jsonl   # your own labeled queries
pytest eval_recall/                                   # metric-logic unit tests
```

## Configurations

| `--config` | What runs |
|---|---|
| `dense` | ChromaDB vector search only (`_vector_search_raw`) |
| `bm25` | BM25 lexical search only (`_bm25_search`, hydrated in BM25 rank order) |
| `hybrid` | dense + BM25 fused with RRF — exactly what the app calls |
| `hybrid+rerank` | hybrid, then the cross-encoder (`ENABLE_RERANKER=1`) |

Each lane is composed from functions `papertrail/retrieval.py` already exposes,
so the ablation exercises the application's real code paths and **required no
changes to `retrieval.py`**.

`hybrid+rerank` needs `pip install -r requirements-reranker.txt`. If the
cross-encoder is unavailable the row is left blank with a stated reason. That
check is deliberate and not optional: `_rerank_chunks` falls back to the fused
order whenever the model is missing — correct for the application, disastrous
for an ablation, since it would silently republish hybrid's numbers under a
rerank label.

## Controlled benchmark

`corpus.py` builds an invented corpus (15 papers, 120 chunks) where relevance is
defined by construction: each paper has one planted result passage, datasets are
shared across papers (so a dataset name alone can't disambiguate), and queries
range from lexically explicit to semantic-only. This makes Recall well-defined
without hand labeling, while staying non-trivial.

Result on this benchmark (all-MiniLM-L6-v2 embeddings):

| Configuration | Recall@1 | Recall@5 | Recall@10 | MRR | Median latency † |
|---|---:|---:|---:|---:|---:|
| dense (Chroma only) | 77.8% | 100.0% | 100.0% | 0.869 | 66 ms |
| BM25 only | 77.8% | 100.0% | 100.0% | 0.870 | 0.3 ms |
| hybrid (RRF fusion) | 77.8% | 100.0% | 100.0% | 0.870 | 67 ms |
| hybrid + cross-encoder rerank | 77.8% | 100.0% | 100.0% | 0.870 | 165 ms |

These are honest numbers on a *constructed* corpus — they validate the pipeline
and the harness, not a claim about arbitrary real papers. Three limits worth
stating plainly:

- **No quality metric separates the configurations.** Recall@1 is identical at
  77.8% across all four and MRR varies by 0.001. Fusion buys nothing measurable
  over plain BM25 here, and the cross-encoder buys nothing for ~3× the latency.
- **Recall@5 saturates at 100%** for all three query types and all four configs,
  so it carries no signal at this corpus size. 120 chunks is a small haystack.
- **A flat result is a fact about the benchmark**, not proof the lanes are
  equivalent. Build a harder labeled set before choosing a configuration on this
  basis.

† Latency is machine-dependent and is deliberately kept out of the committed
report so it regenerates byte-identically; every run prints it, and
`--with-latency` writes it. Spread over four back-to-back runs was 0.01 ms
(BM25), 0.09–0.17 ms (dense/hybrid), and 6.8 ms (cross-encoder) — which is why
no rounding of it is both stable and honest.

The generated report is committed at [`reports/recall.md`](../reports/recall.md)
and is regenerated by re-running the command above.

## Real evaluation

**The `--labeled` flag does not yet evaluate against your own library.** Two
things in `recall_eval.py` stand in the way, both by design for isolation:
`_setup_isolated_state()` repoints `STATE_DIR` at a fresh temp directory before
PaperTrail is imported, so a real library is never loaded; and `main()`
unconditionally calls `index_corpus(papers)` — which resets state and indexes
the *synthetic* corpus — before evaluating. Passing `--labeled` therefore scores
your queries against the invented corpus, where your gold chunk ids do not
exist, and every query registers as a miss.

Making it work needs a code change, not just a JSONL: `main()` would have to
skip `_setup_isolated_state()` and `index_corpus()` when `--labeled` is given,
and point at the real `STATE_DIR` instead. The judgment format itself is already
what you would want — JSONL of
`{"query": ..., "gold_chunk_id": "<paper_id>_chunk_<i>"}`, where the chunk id
matches the ids `add_to_vector_store` assigns at ingest.
